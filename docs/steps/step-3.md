# 第 3 步（3a）：通用回复完成检测

> 给 Muse 的任务指令。分支名：`muse/step-3`。
> **前提：第 2 步（PR #2）已合并到 `main`。** 必须从最新的 `main` 创建分支；如果 `src/content.js` 里没有 `relay.latest` 相关代码，请停下并告诉用户。
> 开始前先读 `README.md`、`docs/PLAN.md`（重点是"状态模型"和"协作协议"）。

## 目标

让每个页面**自己判断**"AI 刚刚把回复写完了"，并在判断成立时把本页写入 `relay.latest`（本页亮红框，其他页面自动熄灭）。不再依赖用户手按快捷键。

这一步只做**通用检测**：不依赖任何站点的选择器，只监视页面内容的变化模式。具体站点的专用适配（3b）留到以后，**这一步不要写任何站点专用的选择器**。

## 只改这些文件

1. `manifest.json`（只把 `version` 改为 `"0.3.0"`，其他不动，不增加权限，不增加站点）
2. `src/content.js`

不要创建别的文件，不要改 `README.md` 或 `docs/`。

## 检测思路

AI 回复是"流式"的：内容会在几秒到几十秒内持续变化，然后停下。所以：

- 监视页面内容变化；
- 把"持续一段时间、且变化量不小的一段连续变化"看作一次**突发（burst）**；
- 突发结束后静止一小段时间，就认为"回复完成"。

## src/content.js 要求

保留第 2 步已有的所有功能（红框、实例 ID、`relay.latest` 同步、快捷键切换），在此基础上新增：

### 1. 可调参数（文件顶部用 `const` 集中定义，带注释）

| 常量 | 初始值 | 含义 |
|---|---|---|
| `QUIET_MS` | 1500 | 无有效变化持续这么久，视为突发结束 |
| `MIN_BURST_MS` | 2000 | 突发从开始到结束至少持续这么久，才可能是回复 |
| `MIN_MUTATIONS` | 30 | 突发中至少有这么多条有效变化记录 |
| `MIN_ADDED_CHARS` | 80 | 突发中新增文字量的估算值至少这么多 |
| `NAV_GRACE_MS` | 3000 | 页面刚加载、或地址（`location.href`）刚变化后，这段时间内的变化一律忽略（避免把"加载历史对话"当成回复） |

这些只是初始猜测值，**后面会根据用户的真实使用调整**，所以必须集中放在一处，方便修改。

### 2. 监视

- 用一个 `MutationObserver` 监视 `document.body`，选项：`{ childList: true, subtree: true, characterData: true }`（不监视 attributes）。
- 对每条变化记录，**先过滤再计数**。以下情况的记录一律忽略：
  - 目标节点（文本节点则取其父元素）在可编辑区域内：`textarea`、`input`、`[contenteditable]` 的后代，或其自身。这是用户在打字，不是 AI 回复。
  - 处于 `NAV_GRACE_MS` 保护期内。
- 对有效记录累计：
  - `mutations += 1`
  - 新增文字量估算 `addedChars`：对 `childList` 记录里每个新增节点，加上 `min(node.textContent.length, 2000)`；对 `characterData` 记录加 1。
  - **只统计长度这个数字，绝不读取、保存或记录文字内容本身。**
- 突发的开始：第一条有效记录出现时开始计时（记录 `burstStart = performance.now()`）。
- 每次有新的有效记录，就重置一个 `QUIET_MS` 的定时器（防抖）。

### 3. 判定

定时器触发（突发结束）时：

- 如果同时满足：持续时间 ≥ `MIN_BURST_MS`、`mutations ≥ MIN_MUTATIONS`、`addedChars ≥ MIN_ADDED_CHARS` → 判定为**回复完成**，调用写入函数把本页写入 `relay.latest`。
  - 注意：这里是**写入**（set），**不是**像快捷键那样"切换"。如果 `relay.latest` 已经是本页，也就是再写一次更新 `ts`，不会清除。
- 无论是否判定成功，都要把计数器（`mutations`、`addedChars`、`burstStart`）重置，准备下一次突发。

### 4. 地址变化与页面加载

- 页面加载完成时，记录一个"保护期结束时间" = 当前时间 + `NAV_GRACE_MS`。
- 检测到地址变化（单页应用跳转）时同样重置保护期。可以用较低频率的定时检查 `location.href`（例如每 1 秒比较一次），**不要**为此给 `history` 打补丁，**不要**引入 `webNavigation` 等权限。
- 保护期内产生的变化不计入突发。

### 5. 调试输出（只含数字）

判定时用 `console.debug` 输出一行，前缀 `[Relay]`，内容只含数字和结论，例如：
`[Relay] burst ended { durationMs: 8200, mutations: 154, addedChars: 1930, accepted: true }`
被拒绝时同样输出，`accepted: false`，用于以后调参。**不要输出任何页面文字内容。**

### 6. 健壮性

- 沿用第 2 步的失效上下文处理：扩展被重新加载后，旧页面里的观察器和定时器要安静停止（`isContextValid()` 为假时 `disconnect()` 观察器并清除定时器，不要报错刷屏）。
- 保证只创建一个观察器，一个定时器。
- 仍然禁止：`eval`、远程脚本、`innerHTML` 拼接、读取或保存页面内容、第三方库、新增权限。
- 代码保持清晰，带注释；检测逻辑建议封装成一个小函数，避免和红框、快捷键代码混在一起。

## 验收标准（Muse 对照自测，用 DOM 桩或模拟）

- [ ] `manifest.json` 合法，`version` 为 `0.3.0`，权限和站点与第 2 步一致
- [ ] 模拟"持续约 5 秒、多次追加文字、然后静止"：判定为完成，写入 `relay.latest`

- [ ] 扩展上下文失效后，观察器和定时器安静停止

## 已知限制（供审查参考，不需要 Muse 解决）

- 页面在后台标签页或被完全遮挡时，Chrome 会降低定时器频率，检测可能延迟。左右分屏且都可见时不受影响。
- 这是通用启发式，可能出现误判（把非回复的大变化当成回复）或漏判（短回复达不到阈值）。用户实测后会反馈，再调参数或做站点专用适配。
